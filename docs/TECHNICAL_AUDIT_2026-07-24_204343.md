## 1. Resumen ejecutivo

La auditoría confirmó y corrigió los tres defectos P0 del inventario y del cursor
USN que podían perder una generación válida, publicar una exploración parcial o
adelantar el cursor más allá de eventos ambiguos. El inventario pasa al esquema
7, conserva filas por generación con clave `(scan_id, path)`, publica sólo
generaciones completas mediante un checkpoint validado y ofrece un lector
atómico `published_snapshots(root)`.

También se corrigieron:

- una migración v1→v2 del catálogo capaz de perder historial mediante
  `INSERT OR IGNORE`;
- el tratamiento falso como `failed` de acciones cuyo efecto real es incierto;
- varias conexiones SQLite que omitían claves foráneas;
- un lector PDF aislado que no abría el estado en modo estrictamente de sólo
  lectura;
- la reutilización semántica de imágenes desde inventarios no publicados;
- el código de salida de validaciones posteriores a `argparse`;
- la documentación operativa, de CLI, persistencia, recuperación, seguridad,
  arquitectura y empaquetado.

Los riesgos `NC-AUD-010`, `011`, `012`, `013`, `015` y parte de
`017` no están totalmente resueltos. No se presenta a NeoCortex como íntegro
en sentido absoluto.

## 10. Defectos nuevos

### NC-AUD-018 — Migración del historial de catálogo podía descartar datos

- **Clase / severidad / confianza / estado:** error confirmado; alto; alta;
  corregido.
- **Ubicación / componente:** `document_catalog_schema.py`, migración v1→v2;
  persistencia de catálogo.
- **Observado / evidencia:** la migración usaba una copia tolerante capaz de
  omitir filas; fixtures poblados y objetos desconocidos demostraron el riesgo.
- **Causa:** contrato legacy superficial más `INSERT OR IGNORE`.
- **Impacto:** pérdida silenciosa de historial o aceptación de una deriva no
  comprendida.
- **Reproducción:** tests parametrizados con columna, trigger y objeto reservado
  desconocidos.
- **Recomendación / cambio:** reconocer sólo el contrato exacto; copiar sin
  `OR IGNORE`; comparar conteos y abortar ante deriva.
- **Pruebas / validación:** cuatro regresiones pobladas; idempotencia, rollback e
  integridad aprobados.
- **Riesgo / efectos:** instalaciones con deriva antes tolerada ahora se
  abstienen; no se descartan datos.
- **Compatibilidad / rollback / prioridad:** compatible con contratos v1
  conocidos; restaurar la copia SQLite consistente y la versión anterior; P0.

### NC-AUD-019 — Estado semántico efectúa consultas/conexiones repetidas

- **Clase / severidad / confianza / estado:** riesgo de escalabilidad; medio;
  media; pendiente.
- **Ubicación / componente:** `semantic_status_service.py` y repositorios
  semánticos; diagnóstico.
- **Observado / evidencia:** inspección muestra agregados separados y aperturas
  repetidas; no se ejecutó benchmark representativo.
- **Causa probable:** composición por repositorios independientes.
- **Impacto:** latencia y contención crecientes con tablas grandes.
- **Reproducción:** no cuantificada; requiere fixture poblado y conteo de
  statements.
- **Recomendación:** medir primero y consolidar sólo agregados compatibles en una
  lectura consistente.
- **Cambio / pruebas / validación:** ninguno; suite funcional aprobada.
- **Riesgo / efectos / compatibilidad / rollback / prioridad:** una
  consolidación incorrecta podría cambiar snapshots; mantener API; rollback
  trivial al no haber cambio; P2.

### NC-AUD-020 — El watcher no tiene exclusión de vida entre procesos

- **Clase / severidad / confianza / estado:** riesgo verificable; medio; alta;
  pendiente.
- **Ubicación / componente:** `watcher.py`, `cli_watcher.py`; watcher.
- **Observado / evidencia:** el lock de runs protege escritores del framework,
  pero dos watchers pueden permanecer vivos, competir y entrar en backoff.
- **Causa:** no existe un lease/lock de vida por raíz+estado.
- **Impacto:** consumo duplicado, ruido y disponibilidad degradada; no se
  demostró corrupción porque el lock de runs abstiene al segundo escritor.
- **Reproducción:** no se iniciaron dos watchers vivos; inspección y contratos de
  lock.
- **Recomendación:** lock de vida identificable y recuperable, sin matar procesos
  por nombre.
- **Cambio / pruebas / validación:** ninguno; watcher funcional aprobado.
- **Riesgo / efectos / compatibilidad / rollback / prioridad:** evitar stale
  locks; cambio futuro compatible; P2.

### NC-AUD-021 — Metadatos de licencia y avisos ausentes

- **Clase / severidad / confianza / estado:** defecto de empaquetado/gobernanza;
  medio; alta; pendiente.
- **Ubicación / componente:** raíz y `pyproject.toml`; distribución.
- **Observado / evidencia:** no hay `LICENSE`, `NOTICE`,
  `project.license` ni inventario de avisos.
- **Causa:** política de licencia no definida.
- **Impacto:** ambigüedad para redistribuir; PyMuPDF declara alternativa
  AGPL/comercial y PySide6 condiciones LGPL/GPL.
- **Reproducción:** inventario del árbol y metadatos del wheel.
- **Recomendación:** Victor/propietario debe elegir licencia y documentar avisos
  de terceros con revisión jurídica apropiada.
- **Cambio / pruebas / validación:** no se inventó una licencia.
- **Riesgo / efectos / compatibilidad / rollback / prioridad:** añadir una
  licencia incorrecta sería peor; no hay rollback; P1 antes de distribución.

## 11. Riesgos potenciales

- raíces solapadas conservan generaciones separadas, pero requieren política
  operativa explícita;
- generaciones `building` abandonadas no tienen retención completa;
- la base semántica y el catálogo siguen publicando por fila;
- el grafo de código conserva una transacción global;
- el watcher carece de lock de vida;
- bases, WAL, logs, modelos y caches carecen de una política total de cuotas;
- rutas UNC, reparses y hard links no tienen equivalencia completa con NTFS
  local;
- los procesos aislados son contención de recursos, no sandbox de seguridad
  completo.

## 13. Migraciones y compatibilidad

### Inventario 6→7

- monotónica y transaccional;
- reconoce el esquema 6 exacto antes de tocar datos;
- preserva filas y metadatos conocidos;
- introduce PK `(scan_id,path)`, FK a `scans`, estados de scan y checkpoint
  booleano;
- valida conteos, bytes y `foreign_key_check`;
- revierte toda la transacción ante estructura o dato inesperado;
- es idempotente al reabrir una base ya 7;
- no admite downgrade mediante `PRAGMA user_version`.

La base viva `dedup.sqlite3` no fue migrada y continúa en metadata 6. El primer
writer 0.4.1 debe ejecutarse sólo después de backup consistente.

cambiar el número: bases v1 conocidas migran preservando datos; cualquier
estructura desconocida causa rollback y abstención.

## 15. Concurrencia y recuperación

- El puntero de inventario y la generación se publican en una transacción.
- `published_snapshots` hace un único JOIN; un lector mantiene su snapshot
  SQLite mientras un writer publica y poda.
- Una exploración parcial conserva la generación anterior.
- Un lote USN ambiguo no aplica cambios parciales ni avanza el cursor.
- Cancelaciones y `BaseException` conservan rollback en los contratos
  revalidados.
- Un worker semántico tardío no sobrescribe un lease recuperado.
- Las acciones inciertas ya no se etiquetan falsamente como fallidas, pero falta
  conciliación idempotente del efecto real.
- Semántica, catálogo y grafo de código aún carecen de publicación generacional
  completa.

## 16. Auditoría de seguridad

No se ejecutaron mutaciones sobre el corpus. Las pruebas de acciones usan
directorios temporales. Se confirmó simulación predeterminada, autorización
explícita, validación de identidad y destino, bitácora y abstención ante
discrepancia.

Permanece `NC-AUD-010`: Papelera y algunos rename/movimientos usan la ruta
después del último preflight. No hay handle/FileId mantenido hasta la syscall.
También se mantienen límites explícitos para ZIP/XML, PNG, PDF, audio,
subprocesos, memoria y tiempo. La ruta de código no ejecuta código observado.

## 29. Instrucciones de rollback

1. Detener watchers y writers; confirmar PID, padre y línea de comandos.
2. Preservar bases, WAL, SHM, logs y el estado `recovery_required`.
3. Crear una copia consistente con `sqlite3.Connection.backup`, no copiar sólo
   el archivo principal abierto.
4. Validar la copia con `integrity_check` y `foreign_key_check`.
5. Restaurar conjuntamente código y bases compatibles. Para volver a 0.4.0,
   restaurar la base dedup esquema 6 tomada antes de migrar; no editar números de
   versión.
6. Si una acción quedó incierta, conciliar origen, destino, identidad y
   bitácora antes de cualquier reintento.
7. Repetir ayuda, versión, tests focales y checks SQLite antes de operar.

La guía completa está en [RECOVERY.md](RECOVERY.md).
